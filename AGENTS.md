# ПРОТОКОЛ РАБОТЫ (обязателен для любой правки; читать перед каждой задачей)

## Главные правила
1. **Одна задача за раз.** Ничего «заодно» не менять.
2. **Сначала воспроизвести** проблему (лог, curl, тест), только потом править код.
3. **Правка минимальная и точечная.** Не переписывать работающее, не добавлять лишнее.
4. **Никогда не деплоить с красными тестами.** Никогда не коммитить без прогона проверок.
5. Если сомневаешься — спросить пользователя, а не догадываться.

## Обязательный цикл правки (все шаги, без пропусков)
1. **Репро**: зафиксировать факт проблемы (журнал/curl/тест).
2. **Правка кода**: минимальная, строго по проблеме.
3. **`./scripts/check.sh`** → должно быть `ALL CHECKS PASSED` (ruff + ≥322 теста (см. ./scripts/check.sh)).
4. **Если менялся webapp** (`webapp/app.js`, `index.html`, `styles.css`, шаблон страницы):
   **`./scripts/gui_check.sh`** → должно быть `GUI-ПРОВЕРКА ПРОЙДЕНА`
   (jsdom: все экраны + очередь/обложка/удаление/папки).
5. **`./scripts/deploy.sh`** → дождаться `>> done`.
6. **Живая проверка**: curl/лог — проблема исчезла И ничего соседнего не сломалось.
7. **Запись в `docs/SESSION_LOG.md`**: что, почему, как проверено.

## Если баг не ловится тестом
Сначала добавить тест, воспроизводящий баг (**regression-first**), затем фиксить.

## Сторож Telegram (обязательный шаг перед работой и после каждого ответа)

**Почему так строго.** Владелец дважды видел «ты не читаешь сообщения», хотя сообщения не терялись:
каждое лежит в надёжном ящике, но пока я занят длинной задачей, сторож не работает — и ответ
задерживается. Поэтому правило: **ящик проверяется на каждом шаге, а сторож стоит всегда**.

Порядок (нарушение = пропущенное сообщение владельца):
1. **В начале каждого хода** (и перед каждой длинной задачей): `tools/tg_inbox.py --unread` — если
   что-то есть, сначала ответить владельцу, потом продолжать работу.
2. **Пока идёт длинная работа**: сторож должен быть запущен (фоновый job), чтобы прерывание пришло
   на ближайшем шаге, а не после всей задачи.
3. **Сразу после того, как сторож сработал** (напечатал сообщение) — ответить и **перезапустить его**.
4. **Перед завершением хода** — проверить `job_list`, что сторож стоит; если нет — запустить.
Если сторож упал по сети/таймауту — это не потеря: сообщение в ящике, поднять сторожа заново.

Входящие сообщения не теряются: каждое пишется в надёжный ящик `data/tg_inbox/inbox.jsonl`
(см. `src/orchestrator/tg_inbox.py`), поэтому пропущенное видно всегда.
```bash
# сторож (запускать на Mac): покажет пропущенное (и сразу выйдет), иначе ждёт новое;
# голосовые расшифровывает настройками видеомейкера (MLX Whisper, large-v3-turbo, ru)
cd ~/orch-work && ./venv/bin/python tools/tg_voice.py --follow
# отметить сообщения, на которые уже ответил (в них и ставить 👍 через tools/tg_say.py --react)
ssh root@100.95.225.71 'cd /opt/orchestrator && ./venv/bin/python tools/tg_inbox.py --ack 224 226'
# расшифровать голосовые вручную (если нужно): tools/tg_voice.py --unread
```
На сервере MLX нет: он только копит голосовые в `data/tg_voice/`, расшифровка — на Mac.
Правила: отвечать только по-русски; 👍 ставить ровно на то сообщение, на которое ответил;
никогда не использовать `--react-last`; сообщение владельца цитировать в чат дословно.

## Скиллы Эмиля Ковальски (подключены 2026-09-23 по просьбе владельца)

Установлены глобально (`~/.agents/skills`, ставится `npx skills@latest add emilkowalski/skills -g -y --agent '*'`),
видны в каталоге скиллов сессии. Перед любой правкой панели **сначала загрузить нужный скилл** (`skill` tool):

- `emil-design-eng` — философия полировки UI, детали, которые делают интерфейс приятным;
- `apple-design` — материалы/глубина, тайминги, прерываемые переходы, reduced-motion;
- `mobile-native` — **обязательно для панели**: она живёт в телефоне внутри Telegram Mini App
  (залипающий hover, вспышка тапа, баг 100vh, зум при фокусе, «резиновый» скролл, вырез экрана).
- Дополнительно по задаче: `review-animations`, `improve-animations`, `find-animation-opportunities`,
  `animate`, `animation-vocabulary`.

Правило: если правка касается `webapp/*` — в отчёте указывать, какой скилл загружен. Наш CSS уже построен
на этих принципах (см. `webapp/styles.css:1`, токены `--ease-out`, `--dur-press`, «Apple/Emil» в шапке).

## Владелец должен видеть, что работа идёт (просьба от 2026-09-23)

Владелец: «можешь как-то показывать что ты в процессе, а то как будто закончил всё и забыл про меня».
У ботов нет «печатает…» по умолчанию, поэтому показываем явно:
1. **Перед длинной работой** — `tools/tg_say.py --typing` (индикатор «печатает…», ~5 секунд).
2. **Работа дольше пары минут** — держать индикатор фоном: `tools/tg_say.py --typing-for 600`
   (запускать фоном, по завершении задачи остановить); плюс короткое сообщение на каждом этапе
   («начал», «правлю», «проверяю», «выкладываю», «готово»).
3. **Молчание дольше пары минут — это ошибка**, даже если работа кипит.

## Главное правило владельца: вылизывать всегда (2026-09-23)

Владелец (msg 281): «Не спрашивай — дошлифовать. Всё должно быть вылизано всегда, запомни это».

Значит:
- **не спрашивать разрешения на дошлифовку.** Нашёл мелочь в виде/поведении — доделывай сразу, в том же
  проходе, а не «предложи владельцу»;
- «мелочь» — это тоже дефект: разный контраст, разъехавшиеся на 2 пикселя края, разные размеры одинаковых
  иконок, скачущие зазоры, обрезанный элемент, шум в журнале;
- прежде чем говорить «готово» — посмотреть на результат **глазами** (скриншот + модель со зрением,
  см. раздел про скиллы), пройтись по списку найденного и закрыть его;
- отчёт владельцу — про результат, без вопросов «делать ли». Вопросы допустимы только про то, что
  действительно знает лишь он (название проекта, содержание контента, доступы).
