3. ЖЁСТКИЕ ПРАВИЛА
   3.1 Прод не ломать. Новое поведение — только за флагом/конфигом; по умолчанию
       работает прежнее. Инварианты: engines остаются youtube: direct, telegram: postiz;
       модульный путь включается только при ORCH_MODULE_PUBLISH=1 и engines.<п>=module:<id>.
   3.2 Никаких серых методов: обход проверок, юзерботы, накрутка, недокументированные
       эндпоинты.
   3.3 Секреты — только .env или выделенное хранилище (права 600). Никогда в git,
       в лог, в БД открытым текстом, в отчёт.
   3.4 Миграции БД — только аддитивные (db.py::_migrate, ALTER TABLE ADD COLUMN).
       Никаких alembic в этом проекте. Никаких переименований и удалений колонок/таблиц.
       После миграции — прогон тестов на существующих данных.
   3.5 Каждая правка — с тестом. Багфиксы regression-first: сначала тест, потом фикс.
       Номер тестов не уменьшать. Текущая база: 649 passed / 5 skipped.
   3.6 Перед КАЖДЫМ коммитом: ./scripts/check.sh → «ALL CHECKS PASSED».
       Скрипт = ruff → python compileall → XSS/CSP → node --check → pytest → vulture.
       Мёртвый код (vulture) не оставлять. Если менялся webapp — дополнительно
       ./scripts/gui_check.sh → «GUI-ПРОВЕРКА ПРОЙДЕНА». Миграционные и GUI-смоуки —
       отдельными скриптами, в check.sh их нет.
   3.7 Git: маленькие коммиты с содержательными сообщениями; push — только после
       зелёного check.sh и только если владелец дал слово на push.
   3.8 Код — строго по 02_MODULE_STANDARD, 03_API_STANDARDS (таксономия ошибок,
       capabilities в манифесте), AGENTS.md. Не плоди параллельные сущности:
       расширяй существующие таблицы и механизмы.
   3.9 Честность отчёта: «готово» — только с выводом команд. Что не проверял —
       так и пиши «проверить актуальность».
   3.10 Не затирай и не коммить чужую незакоммиченную работу. В дереве есть
        M docs/dev/09_YT_SCRIPTS_TZ.txt (черновик ТЗ владельца). Сохранить

4. РЕАЛЬНЫЕ ГРАНИЦЫ ПЛАТФОРМ (не обещай невозможного)
   Скан уже загруженных видео:
     YouTube   — ПОЛНЫЙ: playlistItems(uploads) + videos.list(part=status):
                 privacyStatus (public/unlisted/private) + publishAt (отложенные).
                 Скан дёшев: 1 unit квоты за страницу.
     Facebook  — scheduled_posts (отложенные) + /feed?fields=id,is_published
                 (в т.ч. false) + /videos.
     Threads   — /threads (опубликованные) + /ghost_posts. Нативного планирования нет.
     Instagram — только /media (опубликованные). Черновики, отложенные, контейнеры
                 API не отдаёт.
     TikTok    — POST /v2/video/list, только публичные видео. Inbox/черновики
                 перечислить нельзя.
     Telegram  — скан НЕВОЗМОЖЕН (Bot API не отдаёт историю канала). Источник
                 истины — собственный журнал бота в БД.
     Postiz    — зеркало нашей очереди (list_scheduled), окно −90/+365 дней.
   Платформы с частичным охватом в отчёте помечаются «неполный охват».
   Формулировка «скан завершён, все видео найдены» ЗАПРЕЩЕНА.
   Сопоставление (match_score: title 0.5 / дата 0.3 / длительность 0.2) —
   эвристическое: при score < 0.8 обязательна ручная ревизия перед любым
   действием (claim/delete). Автопривязка с риском удаления чужого видео запрещена.
   Квота YouTube: 10 000 units/сутки, загрузка = 1600 units → ≈6 загрузок в сутки.
   При остатке < 2000 units — отказ с явной ошибкой, не публикация.
   Пока OAuth-приложение в статусе Testing, refresh-токен живёт 7 дней — боевая
   публикация сломается сама. Перевод в «In production» — блокер владельца.

5. ЗАДАЧИ ПО СИСТЕМАМ
   Для каждого пункта: критерий готовности + тесты. Порядок — строго 5.1 → 5.13.

   5.1 ЯДРО: СТАТУСЫ И ССЫЛКИ МОДУЛЬНЫХ ПУБЛИКАЦИЙ  [приоритет 1, делать первым]
       - status_sync сегодня работает только по Postiz. Научи синхронизировать
         модульные публикации: опрос состояния через модуль, запись статуса и
         release_url. Без этого после перехода на модули посты навсегда останутся
         в scheduled, ссылки не появятся, в журнале — «get_post failed».
       - publisher на модульном пути не сохраняет release_url — сохранять сразу.
       - Тесты: отложенная модульная публикация → published + корректный URL;
         публикация через модуль → release_url в БД; ошибка опроса статуса →
         корректная ретрай-семантика без зацикливания.

   5.2 КОНТРАКТ МОДУЛЕЙ: ЛИСТИНГ  [приоритет 1, обязательно ДО любого переключения]
       - Добавить в контракт PlatformModule метод листинга загрузок и capability
         list (none | published | full) в манифест модуля.
       - Почему обязательно: сейчас сканер загрузок строится из движков; при
         engines.youtube: module:youtube авто-скан раз в сутки перестанет работать
         и перестанет видеть уже загруженное — то есть отвалится ровно тогда,
         когда понадобится.
       - Обработка NotSupported по capabilities — понятная ошибка/фолбэк, не падение.
       - Тест контракта для каждого модуля: capabilities, сигнатуры, поведение
         при ошибке.

   5.3 СКАНЕР ЗАГРУЗОК (расширение раздела «Ручные загрузки»)
       - Модель данных: состояние published | scheduled | unpublished (ghost)
         и publish_at в platform_uploads (аддитивная миграция).
       - Панель: колонка состояния и фильтры; честные пометки о неполном охвате
         там, где платформа не отдаёт данных.
       - Реализация листинга по §4 для каждой платформы.
       - Связка с daily_ahead: находить уже загруженные (в т.ч. отложенные) видео,
         чтобы не грузить дубль.
       - Ручная ревизия обязательна при score < 0.8.

   5.4 ДВИЖОК ВЕРСИЙ И СОВМЕСТИМОСТЬ
       - core_min в манифестах сейчас декларативен — нет проверки. Реализовать
         fail-closed: при загрузке модуля с core_min выше текущей версии ядра —
         понятная ошибка, НЕ тихий сбой и НЕ игнор.
       - Политика semver для модулей: bump module_version при изменении контракта;
         описать её в 02_MODULE_STANDARD.
       - Версионировать конфиг-схему: незнакомый ключ в config.yaml — предупреждение,
         а не молчаливое игнорирование.
       - Тесты: несовместимый модуль отклоняется; совместимый — грузится.

   5.5 НАБЛЮДАЕМОСТЬ И АУДИТ
