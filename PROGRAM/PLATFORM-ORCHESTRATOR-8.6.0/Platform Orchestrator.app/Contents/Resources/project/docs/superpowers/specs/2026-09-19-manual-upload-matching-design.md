# ТЗ: Ручные загрузки — распознавание, сопоставление, клеймы и учёт

Дата: 2026-09-19 (ред. 2 — учтены ответы заказчика)
Статус: на финальном ревью (реализация не начата)
Тип: архитектурная фича (модуль оркестратора + UI)

---

## 1. Цель

Заливать видео **вручную** прямо в соцсети (YouTube и др.) без правки описаний, а затем
**одной кнопкой** в панели: найти эти загрузки → «умно» сопоставить с известными сущностями
(VideoMaker/ShortsMaker) → **всегда подтвердить у пользователя** → проверить **клеймы** →
при необходимости отредактировать метаданные → **полностью занести в базу** (связь с сущностью,
ссылка, статус, аудит).

## 2. Термины

- **Сущность** — `long_videos` / `shorts` в БД оркестратора.
- **Ручная загрузка (upload)** — видео, опубликованное пользователем в соцсети в обход Postiz/оркестратора.
- **Клейм** — претензия/ограничение прав (YouTube Content ID). Не путать с обычной ошибкой API.
- **Реконсиляция** — скан публикаций платформы → сопоставление → подтверждение → применение.
- **Кандидат** — пара «upload ↔ сущность» с оценкой.

## 3. Решения по открытым вопросам (зафиксировано)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Источник токенов | **Прямые API платформ**, токены из Postiz (`Integration`). Refresh — штатной механикой Postiz, иначе своим refresh. Обоснование: нужен и листинг, и правка чужого видео — Postiz-провайдеры это не покрывают. |
| 2 | Что редактируем + клеймы | После подтверждения: правка описания/названия/ссылки по шаблонам **и сразу проверка клеймов**. Есть клейм → **warning** + варианты: удалить видео или разбираться по платформе. |
| 3 | Платформы | Адаптеры сразу для всех; включаем по мере готовности, **первым YouTube**. |
| 4 | Окно и расписание | Окно назад настраиваемо (по умолч. 60 дней). Скан — по кнопке **и** по расписанию (по умолч. ежедневно). Плюс отчёт-«план»: сколько загружено/найдено/уже известно, последние по времени. |
| 5 | Что считаем совпадением | Серия + вариант (**vertical ищется среди vertical**), для шортсов — конкретный шортс по названию/порядку. Название обычно совпадает с записью в БД. |
| 6 | Авто-скан | **Нет**, только вручную. Кнопка **на каждую соцсеть** + **общая «Сканировать всё»**. |
| 7 | Конфликты | См. раздел 9.5: при конфликте — блок + предупреждение + перепривязка/игнор, без авто-перезаписи. |
| 8 | Сырые ответы API | **Не храним** целиком. Храним только разобранные поля; `raw_json` — усечённо (≤8 КБ) и только для несопоставленных/конфликтных, удаляем после успешного матча. |

## 4. Границы

В рамках: чтение публикаций каналов, сопоставление, подтверждение, проверка клеймов, правка
метаданных, учёт в БД, отчёт-план, идемпотентность.
Вне рамок: автозаливка (её делает паблишер), аналитика.

## 5. Текущее состояние

- Оркестратор: watcher/scheduler/publisher/status_sync/link_updater/safety, SQLite, webapp API.
- Postiz: публичный API `/public/v1/*`, встроенный MCP; OAuth-токены каналов в таблице `Integration`.
- Панель: i18n RU/EN, MCP оркестратора и Postiz.
- Календарь уже читает реальные посты Postiz.
- В БД **нет** таблиц под внешние загрузки (есть только `shorts.upload_text`) → добавляем **одну** таблицу.

## 6. Защита от «перекрёстного огня»

Ключевое: не спутать **свежий пост, опубликованный Postiz**, с **ручной загрузкой**.

Признаки «ручной» загрузки (все обязательны):
1. `platform_video_id` **отсутствует** в известных источниках:
   `entity_platform_status.postiz_post_id` и в списке постов Postiz (`creationMethod == 'API'`);
2. публикация **не** создана Postiz в текущем окне (сверка id/ссылок);
3. находится в канале/аккаунте нашего `integrationId`.

Если хоть один признак не сходится — помечаем `origin='postiz'` и **исключаем** из кандидатов.

## 7. Функциональные требования

### FR-1. Список публикаций
- Для каждого канала (платформа + `integrationId`) получить последние N публикаций
  (по умолч. 50) в окне `lookback_days`.
- Upsert в реестр по ключу `(platform, platform_video_id)`.
- Пометить `origin` = `manual` | `postiz` (по разделу 6).

### FR-2. Сопоставление
- Для `origin='manual'` и без подтверждённого матча — вычислить кандидатов среди сущностей без
  публикации на этой платформе (раздел 9).
- Жёстко: **vertical ищем только среди vertical**, wide — среди wide.

### FR-3. Подтверждение
- Всегда спрашиваем. Экран: upload ↔ кандидат + альтернативы + уверенность + причины.
- Действия: Подтвердить, Другое (выбор/поиск), Игнорировать, Пропустить.

### FR-4. Проверка клеймов
- Сразу после сопоставления (до применения правок) — проверка клеймов по платформе.
- Есть клейм → `claim_status='claimed'`, warning в UI, действия: «Удалить видео» /
  «Оставить, разбираться» / «Игнорировать клейм».
- Редактирование метаданных при активном клейме — **запрещено** (сначала решение по клейму).
- Ограничение: Content ID-клеймы у канала-владельца доступны не через обычный Data API;
  детальную проверку делаем по доступным полям (`status`, `contentDetails`, region block) и,
  при необходимости, помечаем вручную. См. риск в разделе 15.

### FR-5. Применение
- Связать upload с сущностью (1:1 на платформе), проставить `release_url`, статус `published`.
- Правки описания/названия/ссылки по `description_templates` (при `apply_description=true`).
- Для шортса — ссылка на длинное; для длинного — без ссылки.

### FR-6. Учёт и отчёт-план
- Полный аудит (кто/когда подтвердил, что применилось).
- Отчёт при скане: сколько всего, `manual`/`postiz`, сопоставлено/нет, с клеймами, последние по времени.

### FR-7. Запуск
- Кнопки: **по каждой соцсети** и **«Сканировать всё»**.
- По расписанию (по умолч. 1/сутки), можно выключить.

## 8. UI

Новый раздел **«Ручные загрузки»** (`data-view="manual"`):
- Кнопки запуска: `[YouTube] [Telegram] … [Сканировать всё]`.
- Отчёт-план сверху (кол-во/статусы/последние).
- Карточки: upload (платформа, дата, название, превью) ↔ кандидат (тип, серия, вариант), уверенность.
- Значки: `manual`, `claimed` (красный warning), `confirmed`.
- После подтверждения → тост; при клейме — диалог с выбором действия.

## 9. Алгоритм сопоставления

### 9.1 Сигналы (черновые веса)
| Сигнал | Вес |
|---|---|
| Название (нормализация, fuzzy) | 0.30 |
| Близость даты публикации к дате файла (± окно) | 0.20 |
| Длительность (±2 c, ffprobe vs платформа) | 0.20 |
| Ориентация (16:9 / 9:16) — жёсткий фильтр | 0.15 |
| Порядок/индекс (для шортсов) | 0.10 |
| Текст описания (маркеры) | 0.05 |

### 9.2 Пороги
`score=Σwᵢ·sᵢ`. Высокая ≥0.80, средняя 0.55–0.80, низкая <0.55. Авто-применения нет — всегда подтверждение.

### 9.3 Ограничения
- Сущность уже привязана к платформе → исключить.
- Upload уже подтверждён → пропустить.

### 9.4 Функция compact-скана
Один проход: собрать публикации → отсеять `postiz` → посчитать кандидатов → сохранить топ-1 в строке upload
(альтернативы считаются по запросу, **не хранятся** — меньше кода/данных).

### 9.5 Конфликты (ответ на вопрос №7)
- **Upload уже подтверждён к другой сущности:** не перезаписываем молча. Показываем warning;
  действия: «Перепривязать» (убрать старую связь, применить новую) или «Отмена».
- **У сущности уже есть публикация на этой платформе:** warning; действия: «Заменить» или «Отмена».
- **Несколько равных кандидатов (разница <0.05):** помечаем «требует внимания», выбор только вручную.

## 10. Модель данных (минимально)

Одна новая таблица; альтернативы кандидатов и прогоны не храним в отдельных таблицах
(считаем на лету; сводку прогона пишем в `system_state` и `publish_log`) — чтобы не раздувать код.

```sql
CREATE TABLE platform_uploads (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  platform TEXT NOT NULL,
  platform_video_id TEXT NOT NULL,
  url TEXT,
  title TEXT,
  description TEXT,
  published_at TEXT,
  duration_sec REAL,
  width INTEGER, height INTEGER,
  thumbnail_url TEXT,
  origin TEXT NOT NULL DEFAULT 'manual',      -- manual | postiz
  match_status TEXT NOT NULL DEFAULT 'unmatched', -- unmatched|suggested|confirmed|rejected|ignored
  confidence REAL,
  matched_entity_type TEXT, matched_entity_id INTEGER,
  claim_status TEXT NOT NULL DEFAULT 'unknown',   -- unknown|none|claimed
  claim_info TEXT,
  edit_error TEXT,
  raw_json TEXT,                               -- усечённо, только для unmatched/conflict
  first_seen_at TEXT NOT NULL,
  last_seen_at TEXT NOT NULL,
  UNIQUE(platform, platform_video_id)
);

CREATE UNIQUE INDEX idx_upload_confirmed
  ON platform_uploads(platform, matched_entity_type, matched_entity_id)
  WHERE match_status = 'confirmed';
```

Идентификаторы/защита от коллизий: внешний ключ — только `(platform, platform_video_id)`;
1:1 upload↔сущность на платформе (частичный UNIQUE); сущность↔платформа — существующий
PK `entity_platform_status`. Все применения — в транзакции; повторный confirm идемпотентен.

## 11. API / WebApp

- `POST /webapp/api/manual/scan` `{platform?}` → `{run_id}` (async).
- `GET  /webapp/api/manual/plan` → отчёт-план (кол-во/статусы/последние).
- `GET  /webapp/api/manual/uploads?status=&platform=` → список + лучший кандидат.
- `GET  /webapp/api/manual/uploads/:id/candidates` → кандидаты (на лету).
- `POST /webapp/api/manual/uploads/:id/confirm` `{entity_type, entity_id, apply_edits}`.
- `POST /webapp/api/manual/uploads/:id/reassign` `{entity_type, entity_id}`.
- `POST /webapp/api/manual/uploads/:id/reject` | `/ignore`.
- `POST /webapp/api/manual/uploads/:id/claim-action` `{action: delete|keep|ignore}`.
- MCP: `orch_manual_scan`, `orch_manual_plan`, `orch_manual_list`, `orch_manual_confirm`.

## 13. Интеграции, токены, лимиты

- Токены из Postiz `Integration`; refresh — механикой Postiz (если доступна), иначе свой.
- YouTube: чтение своих видео + `videos.update`, `videos.delete`; учёт квоты (10 000/сутки;
  `videos.update` = 50 ед, `delete` = 50 ед). Учитываем лимит «~5 заливок/сутки» в отчёте-плане.
- Адаптер платформы: `list_uploads()`, `update_metadata()`, `check_claims()`, `delete_video()`.
- Платформа без API правок помечается «read-only».

## 14. Ошибки и идемпотентность

- Retry с backoff; сводка в `system_state`/логе.
- Истёк токен → refresh; не удалось → пометить канал, уведомить в Telegram.
- Правка отклонена платформой → `edit_error`, повтор позже; связь сохраняется.
- Повторный скан — upsert (без дублей); повторный confirm — no-op.

## 15. Риски

1. **Клеймы:** Content ID-клеймы не видны через обычный Data API (нужен CMS API партнёра).
   → проверяем доступные поля, при недоступности — ручная пометка; удаление через API доступно.
2. **Токены/скоупы:** убедиться, что у канала есть нужные права (спайк).
3. **Лимиты платформ:** 5 заливок/сутки и квоты → отчёт-план и мягкие паузы.

## 16. Нефункциональные требования

- Компактность: 1 новая таблица, альтернативы на лету, без лишних сущностей.
- Тесты: скоринг, upsert/идемпотентность, confirm/reassign/reject, клейм-политика, миграции.
- i18n RU/EN для новых строк; логирование в `publish_log`.

## 17. Этапы

- **0. Спайк:** YouTube list/update/delete с токеном Postiz; проверить, что отдаёт про клеймы.
- **1. MVP (YouTube):** реестр + скан + сопоставление + подтверждение + учёт; отчёт-план.
- **2.** Правка метаданных + клейм-политика + расписание.
- **3.** Другие платформы (адаптеры), компактный скан всех.

Критерии приёмки MVP:
- Скан находит ручную загрузку YouTube и предлагает верную сущность (vertical↔vertical).
- Посты, опубликованные Postiz, **не** попадают в кандидаты (защита от перекрёстного огня).
- Без подтверждения ничего не меняется.
- После подтверждения: `match_status='confirmed'`, `entity_platform_status='published'` + `release_url`;
  повторный скан не дублирует.
- Клейм → warning и запрет правок до решения.
