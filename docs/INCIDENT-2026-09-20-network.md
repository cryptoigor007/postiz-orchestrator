# Инцидент 2026-09-20: падение всей домашней сети (Wi-Fi/роутер)

## Симптомы (со слов владельца)
- Wi-Fi «умер» примерно с 13:30 до 15:15 МСК: все устройства сети не могли подключиться/работать.
- Перезагрузка и factory reset роутера, техподдержка провайдера — не помогали.
- Сеть ожила **только после выключения ноутбука-сервера** (pve).
- При повторном включении сервера «ерунда» повторялась.

## Что нашли в логах сервера

### 1. Война маршрутов каждые 2 секунды (главная причина)
- `pve-wifi-route-watchdog.service` (мой скрипт, `while true; sleep 2`) каждые 2 сек делал
  `ip route replace default via 192.168.100.1 dev vmbr0 metric 10` (когда воткнут USB-LAN).
- `route-guard.service` (мой скрипт, `ip monitor route`) мгновенно удалял этот маршрут.
- Результат — непрерывный цикл add/delete default-маршрута:
  - `/var/log/route-guard.log` — **232 492** строки удалений;
  - за 13:00–15:00 — **2 907 RTM_NEWROUTE** и **2 295 `LinkChange: major`** (Tailscale).
- Каждое изменение маршрута заставляло **tailscaled** и **cloudflared** переподключаться
  (DERP rebind, новые QUIC-соединения), а оркестратор — переразрешать DNS
  («Temporary failure in name resolution»). Это непрерывный поток соединений через роутер.

### 2. Форсированные переподключения Wi-Fi
- `net-watchdog.sh` (таймер, раз в 60 сек): если нет default-маршрута —
  `nmcli device disconnect wlp2s0; nmcli device connect wlp2s0`.
- Лог: 13:50, 14:18, 14:19, 14:25, 14:26, 14:27, 14:40, 14:45 — переподключение каждую минуту
  во время сбоя.
- Каждое такое подключение при отсутствии секретов у NetworkManager запускало
  **WPS PBC** (`wps: type pbc start...`, `WPS-PBC-ACTIVE`) — 8 раз за 75 минут.
  В сочетании с кнопкой WPS на роутере это дополнительно дестабилизирует некоторые роутеры.

### 3. Шторм перезапусков сервиса
- `broll-downloader.service` (`Restart=always`, `RestartSec=10`) — счётчик перезапусков
  в прошлой загрузке дошёл до **87 985** (~1200/час), каждый прогон ~2 сек CPU + запись
  в лог (52 МБ). Сеть он не грузил (пулы b-roll были переполнены — 169 ГБ), но создавал
  постоянный мусор (CPU/диск/journal).

### 4. Первый триггер (по логам)
- 13:26:39 — `vmbr0: port 2(enx00e04c36d874) entered disabled state`, `carrier off` (LAN-порт).
- 13:26:40 — `wlp2s0: CTRL-EVENT-BEACON-LOSS` — Wi-Fi роутера пропал (роутер повис/перезагрузился).
- Т.е. в момент X роутер уже под нагрузкой от описанного шторма перестал отвечать, дальше
  сервер своими переподключениями/войной маршрутов не давал ему восстановиться даже после
  reset — ровно как наблюдалось.

## Что сделано (сервер)
1. Выключены и удалены из автозапуска: `pve-wifi-route-watchdog`, `route-guard`,
   `usb-net-monitor`, `broll-downloader` (юнит переименован в `.disabled`).
2. Скрипты `pve-wifi-route-watchdog.sh`, `route-guard.sh`, `network-failover.sh`
   переименованы в `*.disabled` (чтобы никто не запустил вручную).
3. `net-watchdog.sh` переписан в безопасный: **никаких** nmcli-переподключений и `ifreload`;
   только `iw ... power_save off` и рестарт tailscaled, если он упал.
4. NetworkManager: `wifi.scan-rand-mac-address=no`, `wifi.powersave=2` (глобально) и для
   профиля `wd` — `cloned-mac-address=permanent`, `powersave=2` (без рандомизации MAC).
5. `infra_watchdog.py` теперь алертит, если любой из «опасных» юнитов активен или если
   опасный скрипт запущен вручную.

## Профилактика (что проверять при похожих симптомах)
- Никогда не держать два «самолечащих» скрипта, которые правят маршруты/подключения:
  они могут конфликтовать и устраивать шторм.
- Все сетевые watchdog'и — только чтение/логирование, без принудительных реконнектов.
- На роутере желательно: **отключить WPS**, зарезервировать IP (сервер .40, VM .60),
  следить за conntrack (дешёвые роутеры захлёбываются от тысяч соединений).
- Диагностика на сервере: `bash /opt/orchestrator/scripts/network_doctor.sh`
  (двойные интерфейсы, proxy_arp, конфликты), `journalctl -b -1 | grep BEACON-LOSS`,
  `wc -l /var/log/route-guard.log`.

## Постфикс: схема failover (сделано после инцидента)
- LAN приоритетен (vmbr0, metric 100), Wi-Fi резерв (wlp2s0, metric 600) — переключение
  делает само ядро по метрике, без скриптов.
- Единственный владелец LAN-маршрута — `/usr/local/sbin/lan-default.sh`
  (событие udev + сверка раз в 60с; идемпотентно; никогда не трогает Wi-Fi и не рвёт соединения).
- VM-интернет работает через любой аплинк: `vm-nat.service` (MASQUERADE+FORWARD для vmbr0 и wlp2s0).
- Проверено: LAN выдёрнут -> трафик мгновенно уходит на Wi-Fi (host + VM = OK);
  LAN включён -> возвращается на LAN (host + VM = OK).
