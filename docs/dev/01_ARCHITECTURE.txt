  01. АРХИТЕКТУРА СИСТЕМЫ (AS-IS, версия 8.4.55)

Документ описывает систему «как есть» на 24.09.2026, чтобы разработчик понимал,
на что накладывается модульная организация (02_MODULE_STANDARD).

--------------------------------------------------------------------------------
1. НАЗНАЧЕНИЕ СИСТЕМЫ
--------------------------------------------------------------------------------
Оркестратор контента: берёт готовые видео (VideoMaker / ShortsMaker), раскладывает
их по расписанию и публикует на платформы (YouTube, Telegram, далее — другие),
ведёт статусы, ссылки, разбирает ошибки, показывает панель и управляется
Telegram-ботом.

Ключевые свойства:
  * публикация по слотам с защитами (лимиты, warmup, анти-коллизии);
  * связка «YouTube-видео → Telegram-пост со ссылкой»;
  * проектность (проекты/ниши: tochka и др.);
  * всё состояние — в локальной SQLite на сервере;
  * управление: панель (webapp), Telegram-бот, MCP-инструменты.

backlog.py/tail.py — хвост серий, решения «распределить/ждать», вопросы владельцу.

manual_uploads.py / manual_sources.py — ручные загрузки и источники (engines!).
webapp_api.py      — HTTP API панели (+ раздача webapp/), ключ доступа.
backup.py          — бэкапы БД (sqlite backup API), ретенция.

  browser_engine.py  — браузерная автоматизация (экспериментально).
  token_broker_client.py — клиент брокера токенов.

4. ПОТОКИ (AS-IS)
--------------------------------------------------------------------------------
4.1 Скан и появление контента
    watcher → новые файлы в /mnt/video/** → записи в shorts / long_videos →
    очередь (platform_queue_state) по платформам.

4.2 Распределение по слотам
    scheduler/slots: long_video — вт/пт 16:00; shorts_standalone — пн/ср/чт/сб/вс
    12:00 и 18:00; thematic shorts — 20:30.
    Для каждого поста создаётся строка entity_platform_status
      (entity_type, entity_id, platform, status='scheduled'/'ready',
       postiz_scheduled_for, last_error).
    Telegram ставится +15 мин от YouTube (telegram_link_delay_min) и ждёт ссылку.

4.3 Публикация
    publisher.publish(): резерв строки (CAS) → подготовка медиа (media.py) →
      * Telegram (send_via=bot): отправка Bot API (send_post, кнопка, превью);
      * YouTube и остальное: postiz.create_post(...) → Postiz грузит В МОМЕНТ слота.
    Запись postiz_post_id, статус publishing → published/error.

4.4 Синхронизация и ссылки
    status_sync: опрос Postiz по расписанию → published + release_url (COALESCE).
    refresh_telegram_links: как только release_url появился → Telegram-строка
      помечается «ссылка известна» → send_due_telegram_posts отправит пост с
      ссылкой и кнопкой.
    Если ссылки нет: Telegram ждёт release_url_timeout_min (90 мин) → потом
      отправляет БЕЗ ссылки (плейсхолдер). Статус ожидания: last_error=
      'waiting_for_youtube'.
    force_update: ручная установка ссылки — СЕЙЧАС ТОЛЬКО для entity_type=
      'long_video' (ограничение; для шортсов не работает — известный баг).

4.5 Telegram-бот
    Polling Bot API; whitelist allowed_chat_ids; команды: /status /queue /failed
    /pause /resume /platforms /calendar /next_video /next_short /distribute
    /backlog_* /series_end /force_link_update /reload_config /tail /app /help;
    диалоги: missing_url (запрос ссылки), tail-режим, backlog-вопросы.

4.6 Панель
    webapp_api.py отдаёт /webapp/** (UI) и /webapp/api/** (метрики, очередь,
    календарь, force_link, scan, distribute и др.). Доступ по ключу
    (X-Webapp-Key / ?key=), наружу — через cloudflared-туннель.

4.7 Инфраструктура
    Брокер токенов: на Postiz-VM (token-broker.service) читает токены из БД
    Postiz (docker exec psql) и отдаёт по /token?platform=youtube.
    Postiz: отдельная VM (192.168.100.60), self-hosted, единственная реальная
    платформа через него сегодня — YouTube.
    MCP: локальные серверы для ассистентов (оркестратор, Postiz).
    Наблюдаемость: journald (orchestrator.service), publish_log в БД,
    infra-watchdog.py (+timer) шлёт алерты в Telegram.

--------------------------------------------------------------------------------
5. ДАННЫЕ (SQLite: /opt/orchestrator/data/data.sqlite)
--------------------------------------------------------------------------------
Таблицы:
  shorts, long_videos            — сущности контента (описания, хэштеги, пути).
  entity_platform_status         — ПОСТ-СТРОКИ: (entity_type, entity_id, platform)
                                   status, postiz_post_id, postiz_scheduled_for,
                                   release_url, published_at, link_updated_at,
                                   last_error.
  platform_queue_state           — состояние очередей платформ (tail, серии и пр.).
  platform_safety_state          — лимиты/warmup/паузы платформ.
  platform_uploads               — ручные загрузки (manual uploads).
  publish_log                    — журнал действий (entity_type, entity_id,
                                   platform, action, details, created_at).
  system_state                   — key/value настройки (в т.ч. служебные флаги).

Статусы строк (ключевые): ready → scheduled → publishing → published
                          (альтернативы: updating, error, waiting_for_youtube в
                           last_error).

--------------------------------------------------------------------------------
8. ОГРАНИЧЕНИЯ ТЕКУЩЕЙ АРХИТЕКТУРЫ (ПОЧЕМУ НУЖНЫ МОДУЛИ)
--------------------------------------------------------------------------------
1) Платформенная логика размазана: publisher/scheduler/telegram_bot знают
   про особенности YouTube/Telegram (link-режим, +15 минут, waiting_for_youtube).
2) Жёсткая связка с Postiz как единственным «настоящим» загрузчиком; Postiz не
   умеет publishAt (загрузку заранее скрытым с отложенной публикацией).
3) Ограничения-хардкоды: force_update только long_video; claims — заглушка;
   проверка ссылок/текстов специфична для YouTube+Telegram.
4) Нет единого манифеста платформы: возможности, лимиты, правила медиа
   раскиданы по коду и конфигу.
5) Добавление новой платформы (Instagram/TikTok/Facebook/Threads) требует
   правок ядра — вместо добавления одного модуля.

Целевая организация и контракт модуля — в 02_MODULE_STANDARD.txt.
