================================================================================
  02. СТАНДАРТ МОДУЛЬНОЙ СИСТЕМЫ (TARGET) + ПЛАН МИГРАЦИИ
================================================================================
Цель: Любая платформа — это отдельный МОДУЛЬ. Ядро оркестратора не знает
особенностей платформ; модуль реализует контракт и сам инкапсулирует:
авторизацию, API, медиа-требования, публикацию/отложку, статусы, клеймы, ошибки.

--------------------------------------------------------------------------------
1. ПРИНЦИПЫ
--------------------------------------------------------------------------------
1.1 Ядро (core) — то, что не зависит от платформы:
    расписание и слоты, очередь/бэклог, БД и статусы, панель, Telegram-бот,
    лимиты и безопасность, бэкапы, наблюдаемость.
1.2 Модуль (platform module) — один пакет на платформу:
    orchestrator/platforms/<id>/ (id: youtube, instagram, tiktok, facebook, threads).
1.3 Модули работают В ПРОЦЕССЕ оркестратора (in-process, python). Отдельные
    сервисы не обязательны; внешние сервисы (Postiz/n8n) при необходимости
    оформляются как модули-адаптеры.
1.4 Контракт модуля — стабильный и версионируемый. Ядро и модуль связываются
    только через контракт (никаких импортов «внутренностей» ядра в модуль).
1.5 Конфигурация платформы описывается МОДУЛЕМ (pydantic-схема) — ядро
    валидирует общий конфиг, включая модульные секции.
1.6 Всё, что делает модуль, наблюдаемо: записи в publish_log, метрики, алерты.

3. МАНИФЕСТ МОДУЛЯ (manifest.yaml)
--------------------------------------------------------------------------------
Обязательные поля:
  id:            youtube                      # уникальный id
  name:          YouTube
  api_version:   "Data API v3"
  module_version: "1.0.0"                     # semver модуля
  core_min:      "8.5.0"                      # минимальная версия ядра
  auth:
    method:      oauth2_authorization_code    # oauth2 | bot_token | app_credentials
    scopes:      ["youtube.upload", "youtube", "youtube.force-ssl"]
    broker_key:  youtube                      # ключ в токен-брокере
  capabilities:
    publish:            true                  # постинг сейчас
    early_upload:       true                  # загрузить заранее (скрыто)
    schedule_publish:   true                  # публикация по времени на стороне платформы (publishAt)
    update_metadata:    true
    delete:             true
    thumbnail:          true
    claims_check:       auto | manual | unsupported
    video:              true
    image:              false
    text:               false
    stories:            false
  limits:
    posts_per_day: 6                          # рекомендация (предохранитель ядра — safety)
    rate:         { rpm: 60 }
    quota:        { unit: "api_units", per_day: 10000, cost_upload: 1600 }
  media:
    video: { container: mp4, video_codec: h264, audio_codec: aac,
             aspect: ["9:16", "16:9"], max_mb: 256000, max_duration_sec: 10800 }
    thumbnail: { formats: [jpg, png], max_mb: 2 }
  statuses:                                    # маппинг в ядро
    published: [published, live]
    pending:   [processing, scheduled]
    failed:    [rejected, failed]
  docs: MODULE_YOUTUBE.txt                     # ТЗ этого модуля

3.1. ПУБЛИЧНЫЙ ХОСТИНГ МЕДИА (если требуется платформой)
Некоторые платформы принимают медиа ТОЛЬКО по публичному URL (Threads; TikTok —
режим PULL_FROM_URL) — файл нельзя «загрузить», платформа сама скачивает его по
ссылке. Тогда модуль объявляет:
    capabilities.public_media_required: true
Ядро даёт модулю возможность опубликовать файл во временное открытое хранилище:
    module.media_host { base_url, dir, ttl_hours }        # секция конфига
Модуль кладёт подготовленный файл в dir и отдаёт платформе URL base_url/<name>;
после публикации файл удаляется по TTL. Требования безопасности: отдельный
каталог/поддомен только для чтения, непредсказуемые имена, TTL ≤ 24 ч.
ОТКРЫТЫЙ ВОПРОС: конкретный хостинг (nginx на pve / маршрут cloudflared /
внешний CDN) — решается при внедрении первого модуля с этой потребностью.

--------------------------------------------------------------------------------
4. КОНТРАКТ МОДУЛЯ (PlatformModule)
--------------------------------------------------------------------------------
Все методы — с явными таймаутами и повторяемыми исключениями ModuleError.
Названия ниже обязательны; отсутствующие в платформе методы возвращают
NotSupported (ядро учитывает это по capabilities).

  manifest() -> ModuleManifest
      Возвращает манифест (id, capabilities, limits, media, ...).

  validate_config(cfg: dict) -> list[str]
      Проверка секции platforms.<id> (схема — в модуле). Пустой список = ок.

  auth_status() -> AuthStatus
      Проверка авторизации без публикаций: {ok, expires_at, scopes, account}.
      Используется watchdog-ом и панелью (алерт «переподключите аккаунт»).

  prepare(media: MediaSpec) -> PreparedMedia
      Проверки/нормализация параметров (кодеки, соотношение, длительность,
      размер, превью). Возвращает план (какие варианты куда), либо ошибку
      MEDIA_INVALID с человекочитаемой причиной.

  upload(media: PreparedMedia, meta: PublishMeta, when: datetime|None) -> UploadResult
      Загрузка «заранее» (если early_upload=true).
      when — время публикации; модуль сам решает, как придержать (publishAt).
      Возвращает: external_id, url, state (uploaded/hidden/scheduled).

  schedule_publish(external_id: str, when: datetime) -> bool
      Установить/изменить время публикации (publishAt).
      False/NotSupported, если платформа не умеет — тогда ядро использует
      режим «публиковать в момент слота» (см. publish()).

  publish(payload: PublishPayload) -> PublishResult
      Немедленная публикация (для платформ без publishAt, а также для
      «тестового поста»). Возвращает external_id, url, state.

  update_metadata(external_id: str, patch: PublishMeta) -> bool
  delete(external_id: str) -> bool
  get_status(external_id: str) -> PublishStatus
      {state: uploaded|processing|published|blocked|failed|deleted, url, error}

  check_claims(external_id: str) -> ClaimsResult
      {supported: bool, status: none|claimed|unknown, details: str}
      Если платформа не отдаёт клеймы через API — supported=false, и ядро
      использует ручной чекпойнт (см. §7).

  capabilities() -> dict[str, bool]   # дублирует манифест (для совместимости)

Ошибки (единая таксономия; атрибуты: code, message, retryable, action):
  AUTH_EXPIRED     — истёк токен; action: refresh (брокер/модуль) + retry
  AUTH_REQUIRED    — нужно переподключение владельцем; action: alert + пауза
  QUOTA            — квота платформы; action: пауза платформы до сброса
  RATE_LIMIT       — лимит частоты; action: backoff (Retry-After)
  MEDIA_INVALID    — файл не соответствует требованиям; action: ошибка
  PLATFORM_REJECTED— платформа отклонила контент (правила/права); action: ошибка
  CLAIM_BLOCKED    — блокировка/клейм; action: пропуск, взять следующий
  TRANSIENT        — сеть/5xx; action: ретраи с backoff
  FATAL            — непочиняемое; action: ошибка + алерт

--------------------------------------------------------------------------------
5. РЕЕСТР И ВЫБОР МОДУЛЯ
--------------------------------------------------------------------------------
Конфиг: engines.<platform>: "module:<id>" | "postiz" | "n8n" | "browser"
  * "module:youtube"  — наш модуль (целевой режим);
  * "postiz"          — модуль-адаптер Postiz (для будущих соцсетей);
  * старые значения ("direct", "postiz") поддерживаются, но маппятся:
      direct  → module:youtube
      postiz  → модуль-адаптер postiz
Загрузка: platforms.load(cfg) → словарь platform → PlatformModule.
Отсутствие модуля для включённой платформы = ошибка конфигурации (fail-fast,
сообщение в панель/бот), платформа помечается disabled.

--------------------------------------------------------------------------------
6. ДАННЫЕ (расширение схемы)
--------------------------------------------------------------------------------
entity_platform_status получает поля (миграция совместимая, ALTER TABLE):
  module             TEXT    — id модуля, который публиковал (напр. youtube)
  external_id        TEXT    — ID на платформе (video id и т.п.)
  external_sub_id    TEXT    — вспомогательный ID (container_id у Instagram,
                               publish_id/post_id у TikTok, video_id у Facebook)
  publish_mode       TEXT    — early_upload | at_slot | manual
  scheduled_at       TEXT    — время публикации на стороне платформы (publishAt)
  claims_state       TEXT    — unknown | pending | none | claimed
  claims_checked_at  TEXT
Правило: postiz_post_id остаётся для совместимости (может быть NULL при прямой
работе модуля). release_url = канонический URL контента у платформы.

--------------------------------------------------------------------------------
7. КЛЕЙМЫ (общий механизм ядра)
--------------------------------------------------------------------------------
1) Модуль объявляет в capabilities.claims_check: auto | manual | unsupported.
2) Если auto — ядро вызывает check_claims() в чекпойнте (за K часов до слота).
3) Если manual/unsupported (как у YouTube) — ядро поднимает РУЧНОЙ чекпойнт:
   за K часов до публикации бот спрашивает владельца (кнопки):
     [✅ Клеймов нет — публикуем]  [⚠️ Есть клейм — пропустить]
4) По решению «есть клейм»: снять publishAt/удалить, пометить строку
   claims_state=claimed, взять следующий кандидат из бэклога на этот слот
   (механика backlog/next уже существует).
5) Все решения — в publish_log; TTL вопроса и дефолт настраиваются в конфиге
   (analog: missing_url_dialog_ttl_hours).

--------------------------------------------------------------------------------
8. НАБЛЮДАЕМОСТЬ И АЛЕРТЫ
--------------------------------------------------------------------------------
* publish_log: события module.upload.start/done, module.publish.start/done,
  module.claims.checked, module.auth.expired, module.quota.exhausted.
* Метрики: успех/ошибка/латентность по платформе и модулю (metrics.py).
* infra-watchdog: добавить проверки:
    - post-waiting (пост ждёт ссылку > N мин);
    - module.auth.needed (auth_status().ok == false);
    - module.last_error: QUOTA/AUTH_* за последние 24 ч.
* Алерты — в Telegram владельцу (allowed_chat_ids), с антиспамом.

--------------------------------------------------------------------------------
9. ТЕСТИРОВАНИЕ И ПРИЁМКА МОДУЛЯ
--------------------------------------------------------------------------------
Обязательный минимум:
  * unit-тесты с подменяемым HTTP (язык контракта: injectable http, как в
    engines/base и token_broker_client);
  * contract-тест на тестовом канале/аккаунте (test_integration_ids);
  * dry-run режим (без реальной публикации) + тестовый пост;
  * тесты маппинга ошибок (AUTH_*/QUOTA/RATE_LIMIT/MEDIA_INVALID);
  * тесты идемпотентности (повторный запуск не создаёт дубль).
Чек-лист приёмки модуля:
  [ ] манифест заполнен; capabilities честные
  [ ] validate_config + пример конфига в ТЗ
  [ ] auth_status работает и понятен владельцу
  [ ] upload/schedule_publish/publish/update/delete/get_status
  [ ] claims_check (auto или честный unsupported)
  [ ] ошибки маппятся в таксономию §4
  [ ] тесты зелёные; публикация на тестовом канале подтверждена
  [ ] README.txt + ТЗ (docs/modules/MODULE_<ID>.txt) обновлены
  [ ] наблюдаемость: события в publish_log, метрики, алерты
  [ ] откат: описан и проверен (выключить модуль = платформа disabled)

--------------------------------------------------------------------------------
10. ПЛАН МИГРАЦИИ (этапы)
--------------------------------------------------------------------------------
Э0. Документы и стандарт (этот пакет) — согласование.
Э1. Scaffolding: platforms/base.py, manifest.py, registry, загрузка из конфига,
    тесты; старые engines не трогаются (совместимость через маппинг).
Э2. Модуль youtube (эталон): api.py + module.py, режимы early_upload +
    schedule_publish (publishAt) + at_slot; интеграция в publisher/scheduler
    через контракт; миграция схемы БД (ALTER TABLE, безопасно).
Э3. Модуль telegram: перенос текущей Bot API-логики (send_post/delete/edit)
    в модуль; ядро теряет ветвления «send_via=bot».
Э4. Модуль-адаптер postiz: оборачивает текущий PostizClient; ядро не знает
    про Postiz напрямую.
Э5. Переключение: engines.youtube=module:youtube; прогон на тестовом канале;
    боевое включение; мониторинг 3 дня.
Э6. Новые модули (instagram/tiktok/facebook/threads) — по ТЗ из docs/modules.

Принципы миграции:
  * каждый этап — отдельный коммит + тесты; прод не ломается;
  * фиче-флаги: новые пути включаются конфигом (engines.*), откат = вернуть
    прежнее значение;
  * БД только аддитивно (ALTER TABLE), без переименований существующих полей.

11. ОТКРЫТЫЕ ВОПРОСЫ
--------------------------------------------------------------------------------
СТАТУС: все вопросы ниже разобраны — решения и тесты: docs/dev/04_DECISIONS.txt

1) Ручной чекпойнт клеймов: канал связи — бот (по умолчанию) или панель?
2) Ранняя загрузка: за сколько часов грузить (предлагается 24 ч; настраиваемо
   platform.schedule.early_upload_hours).
3) Кто чистит «зависшие» приватные видео при пропуске (оставлять приватным или
   удалять) — решение владельца; по умолчанию: оставлять приватным + пометка.
4) Модульность n8n/browser-движков — оформлять ли как модули (сейчас
   экспериментальные; предлагается оставить адаптерами).
