================================================================================
  03. СТАНДАРТЫ API ДЛЯ ПЛАТФОРМЕННЫХ МОДУЛЕЙ
================================================================================
Обязательны для всех модулей (youtube, instagram, tiktok, facebook, threads и
будущих). Нарушение = модуль не принимается.

--------------------------------------------------------------------------------
1. АВТОРИЗАЦИЯ (OAuth 2.0 / токены)
--------------------------------------------------------------------------------
1.1 Схемы:
    * OAuth 2.0 Authorization Code (+PKCE, если платформа поддерживает) —
      Google, Meta (Facebook/Instagram/Threads), TikTok;
    * долгоживущие Page/Business-токены (Meta) — производные от user-токена;
    * bot_token (Telegram) — токен бота из .env, бессрочный.
1.2 Хранение токенов: ТОЛЬКО token broker (своё файловое хранилище
    /opt/orchestrator/tokens/<platform>.json, права 600). В git и config.yaml
    токены НЕ попадают. client_id/secret — в .env (600), не в git.
1.3 Обновление (refresh): автоматически; за 10 минут до истечения access-token
    или при первой ошибке AUTH_EXPIRED. Refresh-токен не логируется.
1.4 Проверка авторизации: модуль реализует auth_status() без публикаций;
    watchdog вызывает его минимум раз в сутки и алертит владельцу
    («переподключите аккаунт»), если ok=false.
1.5 Ошибки авторизации:
    401/invalid_token → refresh → retry (1 раз);
    refresh не удался → AUTH_REQUIRED → пауза платформы + алерт владельцу.
1.6 Scopes: только необходимые (минимум для функции); список фиксируется в
    манифесте (auth.scopes) и в ТЗ модуля.

--------------------------------------------------------------------------------
2. HTTP-КЛИЕНТ
--------------------------------------------------------------------------------
2.1 Единый клиент (обёртка), настраиваемый на модуль; требования:
    * таймауты: connect 10s, read 60s (для загрузок — отдельные, длинные);
    * User-Agent: "orchestrator/<core_version> (<platform> module/<version>)";
    * TLS-проверка включена всегда, КРОМЕ явных внутренних адресов,
      помеченных в конфиге (verify_tls=false) — только для self-hosted Postiz;
    * логирование: метод, URL, код, длительность; тела — по флагу debug,
      с маскированием токенов/персональных данных.
2.2 Повторы (retry):
    * только для безопасных/идемпотентных операций и ошибок TRANSIENT (5xx,
      таймауты, обрывы соединения);
    * экспоненциальный backoff c jitter: 1s, 2s, 4s, 8s, 16s (максимум 5 попыток);
    * уважать Retry-After (если заголовок есть — ждать указанное);
    * НЕ повторять: 4xx валидации, MEDIA_INVALID, PLATFORM_REJECTED.
2.3 Загрузки медиа:
    * большие файлы — только resumable/chunked протоколы платформы;
    * возобновление после обрыва там, где протокол поддерживает;
    * проверка размера/хеша до и после (при возможности).
2.4 Идемпотентность:
    * перед созданием — проверка «уже существует» (external_id/таблица);
    * операции «создать контент» должны быть защищены от повторного запуска
      после сбоя (сохранять черновик/контейнер-ID до публикации);
    * пример ядра: CAS-резерв строки (publisher._reserve_publish).

--------------------------------------------------------------------------------
3. КВОТЫ И ЛИМИТЫ
--------------------------------------------------------------------------------
3.1 Модуль объявляет в манифесте: публикации/сутки, rpm, quota (единицы/сутки
    и стоимость операций). Пример YouTube: 10 000 units/day, upload = 1600.
3.2 Ядро ведёт счётчики (platform_safety_state) и применяет:
    * отсечку по квоте (QUOTA → пауза до сброса);
    * прогрев/лимиты публикаций (warmup, daily_limit) — уже реализовано в safety;
    * анти-коллизии по времени (min_interval).
3.3 Запрещено обходить квоты несколькими приложениями/аккаунтами — это
    нарушение политик платформ.

--------------------------------------------------------------------------------
4. ЕДИНАЯ ТАКСОНОМИЯ ОШИБОК
--------------------------------------------------------------------------------
(см. 02_MODULE_STANDARD §4; здесь — правила маппинга)
  * 401 / invalid_token            → AUTH_EXPIRED
  * 403 quotaExceeded / limit*     → QUOTA
  * 429 / rate limit               → RATE_LIMIT (backoff по Retry-After)
  * 5xx / timeout / connection     → TRANSIENT
  * 400 validation / unsupported   → MEDIA_INVALID или PLATFORM_REJECTED
  * ограничение/претензия по правам→ CLAIM_BLOCKED
Прочие коды — FATAL. Каждой ошибке модуль обязан дать человекочитаемое
сообщение (русский) для панели/бота: что случилось и что делать.

--------------------------------------------------------------------------------
5. ВЕРСИОНИРОВАНИЕ API
--------------------------------------------------------------------------------
5.1 Версия API фиксируется в манифесте (api_version) и в ТЗ модуля.
5.2 Апгрейд версий: проверка deprecation не реже 1 раза в квартал; апгрейд —
    отдельным коммитом с регресс-тестами.
5.3 Совместимость: модуль объявляет core_min (минимальная версия ядра) и
    module_version (semver). Ядро отвергает модуль с несовместимым core_min.

--------------------------------------------------------------------------------
6. БЕЗОПАСНОСТЬ
--------------------------------------------------------------------------------
6.1 Секреты: .env (600) / tokens (600); маскирование в логах (***);
    запрещено печатать токены в вывод команд.
6.2 Ограничение доступа: токен-брокер — по X-Broker-Secret + allowlist IP;
    панель — по ключу; бот — whitelist chat_id.
6.3 Минимизация данных: наружу уходят только контент и служебные метаданные;
    никаких персональных данных владельца в запросах к платформам.
6.4 Аудит: каждое внешнее действие фиксируется в publish_log (кто/что/когда).

--------------------------------------------------------------------------------
7. НАБЛЮДАЕМОСТЬ
--------------------------------------------------------------------------------
7.1 События publish_log (единый формат action):
    module.upload.start / module.upload.done
    module.publish.start / module.publish.done
    module.update.done / module.delete.done
    module.claims.checked
    module.auth.expired / module.auth.reconnect_required
    module.quota.exhausted
7.2 Метрики на платформу: успех/ошибка/латентность/остаток квоты.
7.3 Алерты (инфра-watchdog → Telegram):
    * посты, зависшие в ожидании > N мин (ссылка/статус);
    * auth_status().ok == false;
    * серия ошибок QUOTA/AUTH_* за сутки;
    * расхождение «опубликовано у платформы, но не отмечено в БД».

--------------------------------------------------------------------------------
8. ТЕСТИРОВАНИЕ (ОБЯЗАТЕЛЬНОЕ)
--------------------------------------------------------------------------------
8.1 Unit: подменяемый HTTP-транспорт (injectable http), проверка запросов и
    маппинга ошибок.
8.2 Contract: тестовый канал/аккаунт (test_integration_ids), тестовый пост,
    проверка всех методов контракта.
8.3 Dry-run: запуск пайплайна без реальных публикаций (флаг конфига).
8.4 Идемпотентность: повторный вызов не создаёт дубликатов.
8.5 Регресс перед боевым включением: минимум 1 публикация каждого типа
    (video/post) на тестовом контуре + откат.

--------------------------------------------------------------------------------
9. ЧЕК-ЛИСТ ИНТЕГРАЦИИ (Definition of Done)
--------------------------------------------------------------------------------
[ ] Авторизация: схема, scopes, хранение, refresh, auth_status
[ ] HTTP: таймауты, ретраи, backoff, Retry-After, маскирование
[ ] Лимиты: объявлены и учитываются; QUOTA/RATE_LIMIT обрабатываются
[ ] Ошибки: полный маппинг в таксономию + человекочитаемые тексты
[ ] Идемпотентность: защита от дублей, возобновление загрузок
[ ] Наблюдаемость: события, метрики, алерты
[ ] Тесты: unit + contract + dry-run (зелёные)
[ ] Документы: MODULE_<ID>.txt актуален; README.txt в модуле
[ ] Безопасность: секреты вне git, доступы ограничены
[ ] Откат: выключение модуля не ломает ядро и данные
