3. ОБЩИЕ ПРАВИЛА КЛЮЧЕЙ И ПЕРЕДАЧИ СЕКРЕТОВ
--------------------------------------------------------------------------------
3.1. Хранение: только .env (600) и кабинеты. В git — `.env.example` с ИМЕНАМИ.
3.2. Передача: владелец кладёт данные в файл на сервере (например
     `root@100.95.225.71:/root/tg_media_owner/apps.env`, 600) или сам вводит
     в кабинет. В чат/почту секреты не отправлять.
3.3. Маскирование: логи/ошибки не содержат токенов; URL с параметрами не печатать.
3.4. Ротация: при подозрении — перевыпуск в кабинете → обновить .env → рестарт
     сервиса (orchestrator / postiz), проверить auth_status.
3.5. Проверка прав после записи: `chmod 600`, `ls -l`; тест `stat` в doctor.

4. YOUTUBE — модуль P2 (+ CLI 09)
--------------------------------------------------------------------------------
4.1. Что уже есть:
     - Канал @testPostiz подключён к Postiz; Postiz хранит YOUTUBE_CLIENT_ID /
       YOUTUBE_CLIENT_SECRET (в контейнере); оркестратор берёт токен через
       токен-брокер (engines.youtube: direct).
     - Два видео опубликованы; кастомные обложки НЕ применились — канал не
       подтверждён (факт 23.09).
4.2. Что нужно внешне:
     [ВЛАДЕЛЕЦ] 1) боевой YouTube-канал;
                2) подтверждение канала по телефону (без него не работают
                   кастомные обложки);
                3) Google Cloud: OAuth-приложение → «In production»
                   (иначе refresh-токен живёт 7 дней);
                4) свои client_id/secret — сейчас они в окружении Postiz,
                   подтвердить, что приложение собственное.
     [GROK]     ключи перенести в `/opt/orchestrator/.env`
                (YT_CLIENT_ID/YT_CLIENT_SECRET), токен — в
                `/opt/orchestrator/tokens/youtube.json` (600, вне git);
                авто-refresh, invalid_grant → алерт (07 §2.4).
4.3. Шаги владельцу (Google Cloud Console, console.cloud.google.com):
     1) создать проект (или взять существующий);
     2) APIs & Services → Library → включить «YouTube Data API v3»
        (для аналитики позже — «YouTube Analytics API»);
     3) OAuth consent screen: External; scopes добавить: youtube.upload,
        youtube, youtube.force-ssl (+ yt-analytics.readonly — фаза 2);
     4) Publish App → статус «In production» (предупреждение «не проверено»
        для своих аккаунтов допустимо);
     5) Credentials → Create credentials → OAuth client ID → Desktop app →
        скачать JSON (client_id/client_secret);
     6) Authorized redirect URIs:
        - Postiz: `https://<адрес-туннеля>/integrations/social/youtube`
        - CLI (loopback): `http://127.0.0.1:8765/` (порт из 09 §3);
     7) передать client_id/secret способом из §3.2.
4.4. Квота: 10 000 units/сутки; videos.insert ≈ 1600 (≈6 загрузок/сутки).
     Общая с Postiz и CLI — вести учёт (CLI §6 09). При нехватке:
     заявка «YouTube API Services – Audit and Quota Extension Form»
     (потребуется сайт/policy — см. P7), подаёт владелец.
4.5. Contract-проверка (ТОЛЬКО тестовый канал testPostiz): upload private +
     publishAt = +10 мин → get_status → published; ссылка сохранена; при
     падении thumbnails.set ссылка НЕ теряется (регресс 24.09).
4.6. CLI 09: `yt auth login` (loopback) на Mac; профили test/prod; токен 600;
     live-прогон — после получения ключей; остальное — по 09 §11.

10. B2 — МЕДИАХОСТИНГ ДЛЯ META (P6.1)
--------------------------------------------------------------------------------
10.1. Зачем: Instagram/Threads принимают только публичный URL (Meta скачивает
      ролик сама). У нас домашняя сеть — публичного входа нет.
10.2. [ВЛАДЕЛЕЦ] backblaze.com → Create Account (без карты) → Bucket
      (например `orch-media-temp`) → Application Key (keyID + applicationKey) →
      передать по §3.2. [GROK] может подготовить пошаговую инструкцию со
      скриншотами, если нужно.
10.3. [GROK] Куда: Postiz как хранилище (`STORAGE_PROVIDER=s3`, endpoint/region/
      keyID/applicationKey) И/ИЛИ оркестратор (`B2_KEY_ID`, `B2_APP_KEY`,
      `B2_BUCKET`, `B2_ENDPOINT`) для media_host P6.1.
10.4. Правила: отдельный бакет только под временные медиа; случайные имена; TTL
      ≤ 24 ч с авто-удалением; без листинга; ключи 600; удалять после публикации.
10.5. Проверка: `curl -I "<ссылка>"` → 200 и `content-type: video/mp4`
      (не HTML) — см. STORAGE-OPTIONS.md.

11. ДОМЕН И ТУННЕЛЬ (стабильные callback URL)
--------------------------------------------------------------------------------
11.1. Проблема: quick tunnel trycloudflare меняет адрес при рестарте → все
      Redirect URI (Meta/TikTok/Google) ломаются.
11.2. Варианты: (а) named Cloudflare tunnel на домене (рекомендуется, бесплатно
      с доменом на Cloudflare); (б) свой домен + DuckDNS/nginx; (в) Postiz Cloud
      (тоже снимает вопрос). Решение — за владельцем; [GROK] готовит точные
      шаги под выбранный вариант.
11.3. При смене адреса обновить: compose (3 переменные) + кабинеты Meta/TikTok/
      Google + перезапуск postiz; прогон `postiz_tunnel_sync.sh` для контроля.
