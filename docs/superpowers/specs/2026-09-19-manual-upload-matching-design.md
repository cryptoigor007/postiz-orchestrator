# ТЗ: Ручные загрузки — распознавание, сопоставление и учёт

Дата: 2026-09-19
Статус: черновик на ревью (реализация не начата)
Тип: архитектурная фича (новый модуль оркестратора + UI)

---

## 1. Цель

Дать возможность загружать видео **вручную** прямо в соцсети (YouTube и др.) без правки
описаний/названий, а затем **одной кнопкой** в панели:
1. найти эти ручные загрузки в соцсетях;
2. «умно» сопоставить их с известными оркестратору видео (VideoMaker/ShortsMaker);
3. **всегда** спросить подтверждение у пользователя (т.к. сопоставление может ошибаться);
4. после подтверждения — отредактировать метаданные (описание/название/ссылка) и
   **полностью занести всё в базу**, связав ручную загрузку с сущностью и серией.

## 2. Термины

- **Сущность** — запись в БД оркестратора: `long_videos` (длинное видео) или `shorts` (шортс).
- **Ручная загрузка (upload)** — видео, опубликованное пользователем в соцсети в обход
  оркестратора/Postiz (через веб-интерфейс платформы).
- **Реконсиляция** — процесс: получить список свежих публикаций платформы → сопоставить с
  сущностями → получить подтверждение → применить.
- **Кандидат** — пара «upload ↔ сущность» с оценкой уверенности.
- **Вебхук/событие** вне области: интеграция по API-поллингу, без серверных вебхуков платформ.

## 3. Роли и участники

- **Пользователь** — загружает видео вручную; подтверждает сопоставления в панели.
- **Оркестратор** — хранит сущности, запускает реконсиляцию, применяет правки, пишет в БД.
- **WebApp (панель)** — экран «Ручные загрузки»: список найденного, карточки совпадений,
  кнопки подтверждения/выбора/игнорирования.
- **Postiz** — хранилище OAuth-интеграций каналов (токены), источник `integrationId`.
- **Платформы** — YouTube Data API (первым), далее — остальные.

## 4. Границы

В рамках:
- Чтение списка последних публикаций каналов, подключённых в Postiz.
- Сопоставление с сущностями, ручное подтверждение, применение правок, учёт в БД.
- Идемпотентность и защита от двойных привязок/дублей.

Вне рамок (на будущее):
- Автоматическая загрузка видео в соцсети (это делает существующий паблишер).
- Аналитика/статистика.
- Платформы, у которых нет API для чтения публикаций канала.

## 5. Текущее состояние (что уже есть)

- Оркестратор: `watcher` (сканирует папки VideoMaker/ShortsMaker), `scheduler`, `publisher`,
  `status_sync`, `link_updater`, `safety`, БД SQLite, webapp API (`/webapp/api/*`).
- Postiz: публичный API `/public/v1/*` (посты, upload, интеграции, status, release-id),
  встроенный MCP `/api/mcp`.
- Панель: разделы Статус/Папки/Календарь/Очередь/Платформы/Хвост/Ошибки/Метрики/Действия/Справка,
  i18n RU/EN, MCP оркестратора и Postiz для ИИ.
- OAuth-токены каналов лежат в Postiz (таблица `Integration`).
- Календарь уже умеет читать реальные посты Postiz (`GET /public/v1/posts`).

## 6. Ключевая техническая проблема (риск №1)

Чтобы «найти» ручные загрузки и «отредактировать» их, нужен доступ к API платформы от имени
владельца канала (OAuth). Варианты:

- **A. Прямые API платформ, токены берём из Postiz.**
  Читаем `Integration.token/refreshToken` из `postiz-db`; обновление токена — через механику
  Postiz (`RefreshIntegrationService`) или свой refresh. Даёт и листинг, и правку.
  Минус: работа с токенами/скоупами, сложнее.
- **B. Через методы провайдера Postiz** (`/public/v1/integration-trigger/:id`).
  Переиспользуем Postiz. Минус: покрытие методов неизвестно, «правки чужого видео» может не
  поддерживаться.
- **C. Полу-ручной режим.** Пользователь вставляет ссылки на свои видео; читаем публичные
  метаданные (oEmbed/API по id) без OAuth; правка всё равно требует OAuth.
  Минус: нет авто-поиска, правка ограничена.

**Рекомендация:** вариант **A** для YouTube (листинг + `videos.update`), адаптеры под другие
платформы позже. До реализации — короткий **спайк** (проверка скоупов/refresh на реальном канале).

## 7. Функциональные требования

### FR-1. Список ручных загрузок
- Для каждой платформы с подключённым каналом получить последние N публикаций (по умолчанию 50,
  настраивается), с полями: id, url, title, description, publishedAt, duration, разрешение,
  миниатюра.
- Хранить/обновлять в реестре `platform_uploads` (upsert по `(platform, platform_video_id)`).

### FR-2. Умное сопоставление
- Для каждой загрузки без подтверждённого матча вычислить кандидатов среди сущностей, которым
  ещё не назначена публикация на этой платформе, по сигналам (раздел 9).
- Сохранить топ-K кандидатов и уверенность.

### FR-3. Подтверждение пользователем
- Экран показывает загрузку и лучший матч + альтернативы; **всегда** требуется подтверждение.
- Действия: «Подтвердить», «Выбрать другое», «Не моё / игнорировать», «Пропустить».
- Массовое «Подтвердить все с высокой уверенностью» — допустимо, но по явному действию.

### FR-4. Применение после подтверждения
- Связать загрузку с сущностью (1:1 на `(платформа, сущность)`).
- При необходимости обновить метаданные публикации на платформе (описание/название/ссылка) по
  шаблонам `description_templates`.
- Проставить сущности статус `published` и `release_url` = ссылка на публикацию в
  `entity_platform_status`.
- Обновить связи (long ↔ shorts), если применимо.

### FR-5. Учёт в БД
- Все найденные загрузки и результаты сопоставления сохраняются (включая отклонённые).
- Полный аудит: кто/когда подтвердил, какие правки применились.

### FR-6. Ручной запуск и безопасность
- Реконсиляция запускается кнопкой (и опционально по расписанию, выключено по умолчанию).
- Ограничение частоты обращений к API платформ; уважение лимитов.

## 8. Пользовательский флоу (UI)

Новый раздел **«Ручные загрузки»** (`data-view="manual"`):
1. Кнопка **«Найти загрузки»** → запускает реконсиляцию (поллинг статуса).
2. Список карточек: слева — загрузка (платформа, дата, название/превью), справа — предлагаемая
   сущность (тип, серия, порядок), уверенность (высокая/средняя/низкая), причины совпадения.
3. Кнопки: **Подтвердить**, **Другое** (список кандидатов/поиск по сущностям), **Игнорировать**.
4. Раздел «Требуют внимания» (низкая уверенность / несколько равных кандидатов).
5. После подтверждения — тост «Внесено в базу»; сущность помечается published, ссылка сохранена.

## 9. Алгоритм сопоставления

Сигналы и веса (черновые, уточняются спайком):

| Сигнал | Вес | Комментарий |
|---|---|---|
| Совпадение нормализованного названия (fuzzy, язык) | 0.30 | серия/название шортса |
| Близость даты публикации к дате создания файла (± окно) | 0.20 | дельта в часах/днях |
| Совпадение длительности (±2 c) | 0.20 | ffprobe локального файла vs платформа |
| Соответствие ориентации (16:9 / 9:16) варианту сущности | 0.15 | wide/vertical |
| Порядок/индекс (для шортсов внутри серии) | 0.10 | ожидаемая последовательность |
| Текст описания (если есть) содержит маркеры | 0.05 | ссылки/хештеги |

- Итог: `score = Σ wᵢ·sᵢ` (0..1). Пороги: **≥0.80** высокая, **0.55–0.80** средняя, **<0.55** низкая.
- Никогда не применяем автоматически: даже при высокой уверенности — подтверждение.
- Жёсткие ограничения: сущность уже привязана к платформе → исключить; загрузка уже
  подтверждена → пропустить.
- (Опционально, позже) LLM как тай-брейкер при нескольких близких кандидатах.

## 10. Модель данных и миграции

Новые таблицы (SCHEMA_VERSION +1):

```sql
CREATE TABLE platform_uploads (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  platform TEXT NOT NULL,
  platform_video_id TEXT NOT NULL,
  url TEXT,
  title TEXT,
  description TEXT,
  published_at TEXT,
  duration_sec REAL,
  width INTEGER, height INTEGER,
  thumbnail_url TEXT,
  raw_json TEXT,
  match_status TEXT NOT NULL DEFAULT 'unmatched', -- unmatched|suggested|confirmed|rejected|ignored
  confidence REAL,
  matched_entity_type TEXT, matched_entity_id INTEGER,
  matched_at TEXT, confirmed_by TEXT,
  first_seen_at TEXT NOT NULL, last_seen_at TEXT NOT NULL,
  UNIQUE(platform, platform_video_id)
);

CREATE TABLE match_candidates (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  upload_id INTEGER NOT NULL REFERENCES platform_uploads(id) ON DELETE CASCADE,
  entity_type TEXT NOT NULL, entity_id INTEGER NOT NULL,
  score REAL NOT NULL, reasons_json TEXT, created_at TEXT NOT NULL,
  UNIQUE(upload_id, entity_type, entity_id)
);

CREATE TABLE reconcile_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  platform TEXT, started_at TEXT NOT NULL, finished_at TEXT,
  stats_json TEXT, created_by TEXT
);

CREATE UNIQUE INDEX idx_upload_confirmed
  ON platform_uploads(platform, matched_entity_type, matched_entity_id)
  WHERE match_status = 'confirmed';
```

Идентификаторы и защита от «перекрёстных кодов»:
- Внешний ключ учёта — только `(platform, platform_video_id)` (UNIQUE).
- Загрузка ↔ сущность: 1:1 на платформе (частичный UNIQUE-индекс выше).
- Сущность ↔ платформа — существующий PK `entity_platform_status(entity_type, entity_id, platform)`.
- Все применения — в одной транзакции; повторное подтверждение идемпотентно (no-op).

## 11. API / WebApp

- `POST /webapp/api/manual/scan` — запустить реконсиляцию (async), вернуть `run_id`.
- `GET  /webapp/api/manual/runs/:id` — статус прогона.
- `GET  /webapp/api/manual/uploads?status=suggested` — список загрузок + лучший кандидат.
- `GET  /webapp/api/manual/uploads/:id/candidates` — кандидаты с причинами.
- `POST /webapp/api/manual/uploads/:id/confirm` — `{entity_type, entity_id, apply_edits:bool}`.
- `POST /webapp/api/manual/uploads/:id/reject` — отклонить/игнорировать.
- `POST /webapp/api/manual/uploads/:id/reassign` — вручную выбрать сущность.
- MCP-инструменты: `orch_manual_scan`, `orch_manual_list`, `orch_manual_confirm`.

## 13. Интеграции, токены, лимиты

- Токены: из Postiz `Integration` (по `providerIdentifier`), обновление — через Postiz либо свой
  refresh (решается в спайке).
- YouTube: скоупы для чтения своих видео и `videos.update`; учёт квоты (10 000 ед/сутки;
  `videos.list` дешёвый, `videos.update` — 50 ед).
- Ограничение параллелизма; батчинг; кэширование `videos.list`.
- Прочие платформы — адаптеры `list_uploads()` / `update_metadata()`; при отсутствии API —
  платформа помечается «не поддерживается».

## 14. Ошибки и идемпотентность

- Сетевые ошибки — retry с backoff; фиксируем в `reconcile_runs.stats_json`.
- Токен истёк — refresh; при неудаче — пометить канал и уведомить (Telegram).
- Применение правок: если платформа отклонила правку — матч сохраняем, помечаем `edit_error`,
  повтор позже; БД уже консистентна.
- Идемпотентность: повторный скан не создаёт дублей (upsert по ключу), повторный confirm — no-op.

## 15. Безопасность

- Доступ к экрану — только whitelisted Telegram-пользователь/ключ (как остальная панель).
- Токены платформ не покидают сервер; в панель не отдаём.
- Правки метаданных выполняются только по явному подтверждению.

## 16. Нефункциональные требования

- Скан ≤ N обращений к API на канал, устойчив к частичным сбоям.
- Все операции логируются (`publish_log` + отдельный лог реконсиляции).
- Покрытие тестами: алгоритм скоринга, upsert/идемпотентность, confirm/reject, миграции.
- i18n RU/EN для новых строк; доступность (тач-таргеты, фокус).

## 17. Этапы

- **Этап 0 (спайк):** проверить листинг+правку YouTube с токеном Postiz; зафиксировать API/скоупы.
- **Этап 1 (MVP, YouTube):** реестр + скан + сопоставление + подтверждение + учёт в БД
  (правка описания — опционально).
- **Этап 2:** правка метаданных по шаблонам; связь long↔shorts; расписание сканов.
- **Этап 3:** другие платформы (адаптеры), LLM-тай-брейкер (опц.).

Критерии приёмки MVP:
- Скан находит ручную загрузку YouTube и предлагает правильную сущность.
- Без подтверждения ничего не меняется.
- После подтверждения: `platform_uploads.match_status='confirmed'`, `entity_platform_status`
  = `published` с `release_url`; повторный скан не дублирует.
- Отклонённые/низкоуверенные не применяются.
